# notesearch — 実装レポート

## ステータス: 完了(保留中の質問なし)

notesearch_detail.mdの全機能(モジュールA・B・C)を実装しました。
「LLM APIを呼んで回答を得る機能はスコープに含めてください」とのご回答に
基づき、Gemini API連携(`--ask`)も実装しています。依存関係のサイズは
実測で約1.2GB増加(既存venv 500MB→1.7GB)、5GB上限には全く達していません。

## 完了した機能

### アーキテクチャと処理パイプライン
- **チャンク化(ハイブリッド戦略)**: Markdown `#`見出しでの分割を第一段階、
  各セクションが長すぎる場合(または見出しが全く無い場合)は固定文字数
  (デフォルト500文字)+オーバーラップ(50文字)で機械的に分割。各チャンクの
  開始行番号も追跡し、エディタジャンプで実際の行に飛べるようにしました
  (仕様書に明記はありませんでしたが、「該当行へ直接ジャンプ」という
  要求を満たすために実装しました)
- **エンベディング**: SentenceTransformers
  `paraphrase-multilingual-MiniLM-L12-v2`、遅延ロード(実際に埋め込みが
  必要になるまでモデルをダウンロードしない設計)
- **ベクトルDB**: ChromaDB(`~/.notesearch/db`に永続化)
- **ハイブリッド検索**: ChromaDBのベクトル類似度検索とrank_bm25の
  キーワード検索を独立に実行し、両者をmin-max正規化した上で加重和
  (デフォルト50/50)で統合

### モジュールA: DB同期とメンテナンス
- **JITシンク(デフォルト)** — 検索実行時にファイルのmtimeと既存インデックス
  を比較し、新規・変更分のみ差分ベクトル化
- **デーモン同期(watchdogベース)** — `notesearch daemon start`。
  ファイル変更をデバウンス(デフォルト5秒間隔でまとめて再同期)
- **手動同期** — `notesearch sync`
- **ゴーストデータのパージ** — `notesearch clean`。ディスク上に存在しない
  ファイルのチャンクをインデックスから削除

### モジュールB: メタデータとフィルタリング
- source/directory/heading/last_modified(+start_line)をメタデータとして保存
- `--dir`/`--days`フィルタ(ChromaDB側の`where`句 + BM25側は同じ条件で
  手動フィルタしたコーパスから再構築、両者のスコープを一致させています)

### モジュールC: ユーザーインターフェース
- **TUIインタラクティブプレビュー** — msvcrt(Windows専用標準ライブラリ)
  ベース。Enterで該当チャンクの行番号へVS Code等で直接ジャンプ
- **RAGプロンプト・クリップボード連携(`--copy`)** — 仕様書記載の
  フォーマットをそのまま実装
- **Gemini連携(`--ask`)** — ご要望に基づき追加。REST API直叩き
  (`reqretry`経由、リトライ付き)。モデルは`gemini-2.0-flash`をデフォルトに
  設定。APIキー取得手順(Google AI Studio)をREADMEに詳細に記載

## テスト

`pytest notesearch/tests` — **101件全てパス**。

**実際のロジックをそのまま検証した部分**: チャンク化、ファイルスキャン、
設定読み込み、BM25、ハイブリッドスコア統合、RAGプロンプト整形、
エディタコマンド構築、JIT同期/クリーンのロジック(フェイクIndexStore経由)、
そして**ChromaDB自体も実際に使用**(`FakeEmbedder`というハッシュベースの
決定的な小さいベクトルを返すダミーを注入し、実際のSentenceTransformers
モデルはロードしないが、ChromaDBのpersistent client・upsert・query・delete
は全て実物を使用してテストしています)。

**モック化した部分(動作未実機確認、summaryへの記載指示に基づく)**:
- **実際のSentenceTransformersモデル**: `[ocr]`的な重い依存のため、
  実モデルのダウンロード・推論はテストで実行していません。実際に使う際は
  `notesearch "query"`を実データに対して実行して確認してください。
- **実際のGemini API**: `notesearch/tests/test_gemini.py`で`responses`
  ライブラリを使ってHTTPレイヤーをモック化しています(このリポジトリの
  他プロジェクト、例えばtranslate-commentsのDeepLテストと同じパターン)。
  実際のAPIキーでの動作確認はしていません。
- **`watcher.py`のデーモンループ本体**: 実際のファイルシステム監視
  (watchdog)自体は自動テスト対象外です。
- **`tui.py`のインタラクティブループ本体**: msvcrtでのキー入力ループ
  自体はテスト対象外(snapclipの`history` TUIと同じ判断)。

## 発生した問題・設計判断

1. **重大なバグ(実装中に発見・修正済み): CLIのコマンドルーティング**。
   仕様書のCLI例(`notesearch "query"` のようにサブコマンド無しで検索
   できる一方、`notesearch daemon start`のようなサブコマンドも必要)を
   素直にTyperの`@app.callback(invoke_without_command=True)` +
   位置引数`query`で実装したところ、Clickの仕様上「グループの最初の
   トークンは常にサブコマンド名として解決される」ため、`notesearch sync
   --config x`が「`query="sync"`として解釈され、続く`--config`を
   サブコマンド名として探そうとしてエラーになる」という致命的な不具合が
   ありました。カスタムの`TyperGroup`サブクラス(`DefaultCommandGroup`)
   を実装し、「最初のトークンが登録済みサブコマンド名でなければ`search`
   コマンドを補完してから解釈する」という設計に変更して解決しています。
   これはnpm等の一部CLIでも使われる一般的なパターンです。
   実際にコンパイル済みのコンソールスクリプトで動作確認済みです。
   **既知の制限**として、検索クエリが偶然`sync`/`clean`/`daemon`と
   完全一致する場合はそちらのサブコマンドとして解釈されてしまいます
   (READMEに明記)。
2. **エディタジャンプコマンドの構築ロジック**: 当初「テンプレートの最後の
   トークンだけに{path}/{line}を埋め込む」設計でしたが、`vim +{line}
   {path}`のようにプレースホルダーが複数トークンに分かれるテンプレートに
   対応できないことに気づき、「全トークンに対して`.format()`を適用する」
   方式に改善しました(プレースホルダーの無いトークンはformat()が
   無変更で通すため、副作用なく両対応可能)。
3. **BM25の小規模コーパスでの挙動**: rank_bm25の古典的Okapi BM25実装は、
   検索語が文書の半数以上に出現すると負のIDFになり得ます(統計的には
   正しい挙動:「ありふれた語」とみなされる)。テスト作成時にこれで
   ハマったため、READMEとコード内コメントに明記しました。
4. **`.gemini_api_key`の設定経路**: `Settings`データクラスに
   `gemini_api_key`フィールドを追加し、confload経由の設定ファイルまたは
   環境変数`GEMINI_API_KEY`から読み込む設計にしました(translate-comments
   の`DEEPL_API_KEY`と同じパターン)。
